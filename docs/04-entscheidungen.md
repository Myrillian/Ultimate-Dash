# Entscheidungen

> Getroffen am 05.11.2026 von Matthias. Neue Entscheidungen werden unten angehängt.

| # | Thema | Entscheidung | Begründung / Hinweise |
| --- | --- | --- | --- |
| 1 | Konfiguration | SQLite-Datei als Speicher, Bearbeitung im UI, YAML-Export/Import | Vorgabe: Datenbank nur, wenn nötig. Sie ist nötig, weil UI-Editor, IPAM-Daten (Netze, Gruppen, Bereiche), Änderungsprotokoll und gleichzeitige Schreibzugriffe mit reinen YAML-Dateien fehleranfällig werden (Kommentare gehen beim Zurückschreiben verloren, keine Transaktionen). SQLite ist trotzdem die einfachste Form: eine Datei in `/data`, kein eigener Datenbankserver, Backup durch Kopieren. |
| 2 | Tech-Stack | Durchgängig TypeScript: SvelteKit (SPA) im Frontend, Fastify im Backend, gemeinsames Paket für Typen und Validierung (Zod) | |
| 3 | Benutzer | Lokaler Admin plus optional OIDC, Rollen „Admin“ und „Nur lesen“ (später „Benutzer“, siehe 16) | |
| 4 | Reihenfolge | Erst Kern-Dashboard, dann IPAM | Schwerpunkt auf Performance und guter Bedienbarkeit nach Best Practices (Barrierefreiheit, Tastaturbedienung, schnelle Ladezeiten, mobile Nutzung). |
| 5 | DHCP | Technitium ist DNS- und DHCP-Server | Das IPAM kann Leases, Reservierungen und Scopes vollständig verwalten. |
| 6 | Infrastruktur-Module | Rack-Ansicht und Switch-Management später als eigene Module | Switch-Management: Switches, Ports und deren Belegung verwalten (siehe Architektur, Phase 4). |
| 7 | Repo | Vorerst privat, Open Source eventuell später | Lizenz wird bei Veröffentlichung entschieden. |
| 8 | Technitium-Zugang | API-Token in der SQLite-Datei (oder per Umgebungsvariable), Aufrufe nur über das Backend, kurzer Zwischenspeicher (15 s) | Das Token verlässt den Server nie. Mehrere offene Dashboards teilen sich einen Abruf, damit Technitium nicht unnötig belastet wird. Das Token wird als `Authorization: Bearer` (ab Version 15) und zusätzlich als Formularfeld `token` (ältere Versionen) geschickt, per POST, damit es nicht in Zugriffslogs auftaucht. Empfehlung: eigener Technitium-Benutzer mit nur den nötigen Rechten. Getroffen am 06.11.2026 (Claude, im Rahmen der Freigabe für Phase 2). |
| 9 | Änderungsprotokoll | Jede schreibende Aktion an Technitium wird in der Tabelle `audit_log` mit Benutzer, Zeit, Aktion und Ergebnis gespeichert, ein Jahr lang | Grundlage für die spätere Protokoll-Ansicht im IPAM. Fehlgeschlagene Versuche werden ebenfalls festgehalten. |
| 10 | IPAM-Daten | Netze, Kategorien und IP-Bereiche liegen in der eigenen SQLite-Datenbank; die Belegung wird bei jeder Ansicht aus Technitium berechnet (Leases, Reservierungen, DNS-A-Einträge), nicht gespeichert | Es gibt nur eine Wahrheit (Technitium) und nichts zu synchronisieren. Kategorien sind reine Anzeige und ändern nichts in Technitium. Netze dürfen sich nicht überschneiden (/16 bis /30), Bereiche liegen innerhalb ihres Netzes und überschneiden sich nicht. Farben werden als Schlüssel der geprüften Palette gespeichert, nicht als Farbwert. Ein Konflikt ist: zwei verschiedene MAC-Adressen beanspruchen dieselbe IP. Getroffen am 06.11.2026 (Claude). |
| 11 | Abgleich IPAM ↔ Technitium | Belegung ist immer live aus Technitium. Netze und DHCP-Pools werden auf Knopfdruck aus den Scopes übernommen (Vorschlagsliste), Abweichungen beim Gateway werden angezeigt und lassen sich einzeln übernehmen. Es gibt keine automatische Synchronisation und keine Schreibzugriffe auf Technitium. | Ein stiller Hintergrundabgleich würde bewusst gepflegte Netze und Bereiche überschreiben. Ein Netz entspricht einem Scope, wenn die Netzadresse gleich ist; es gibt keine feste Verknüpfung, damit Umbenennen in Technitium nichts kaputt macht. Getroffen am 06.11.2026 (Claude). |
| 12 | Ping-Prüfung | Der Server pingt per System-`ping` regelmäßig (Standard 30 Minuten) alle Adressen der Netze bis /22, die „Per Ping prüfen“ aktiv haben, höchstens 32 gleichzeitig. Antworten werden in `ipam_hosts` gespeichert; Unbekannte erscheinen als „entdeckt“, Admins bestätigen oder vergessen sie. | ARP scheidet aus, weil es nur im eigenen Netz funktioniert; ICMP geht über Netze hinweg, solange der Server sie routet. Node kann ohne Root keine rohen ICMP-Pakete senden, daher das Systemprogramm (im Docker-Image per iputils-ping). Entdeckt heißt: antwortet, steht aber weder in DHCP noch im DNS. Nicht antwortende Geräte (Ping blockiert) bleiben unentdeckt, das ist eine bekannte Grenze. Getroffen am 06.11.2026 (Claude). |
| 13 | Vereinheitlichte IP-Verwaltung | Die IP-Adresse ist der Mittelpunkt: eine IP-Ansicht (Raster und Liste) mit Seitenfenster für DHCP, DNS und Erreichbarkeit; DNS-Zonen und DHCP-Scopes bleiben als Unterseiten. DNS wird beim Anlegen und Umwandeln standardmäßig mitgeführt, ist aber änderbar. Statische IPs im DHCP-Pool werden nur mit Warnung erlaubt. | Siehe `docs/05-ip-verwaltung.md`. Eine laufende Lease lässt sich in Technitium nicht ändern, nur freigeben oder umwandeln. Zusätzlich: Hersteller aus der MAC (mitgelieferte OUI-Liste), nur eine IP pro Anlegevorgang, gespeicherte Ansichten pro Benutzer bei gemeinsamen Daten, ohne Admin-Rolle nur Leserechte in IPAM, DHCP und DNS. Das Dashboard (Gruppen und Dienste) wird pro Benutzer geführt. Abgestimmt am 06.11.2026 mit Matthias (Claude). |
| 14 | Dashboard pro Benutzer | Gruppen gehören einem Benutzer (`groups.user_id`, Services hängen an der Gruppe); der Titel liegt je Benutzer in `settings` (`title:<id>`). Jeder angemeldete Benutzer bearbeitet, importiert und exportiert sein eigenes Dashboard, fremde IDs sind „nicht gefunden“. Kopieren aus anderen Dashboards ist für jeden Benutzer erlaubt, erstellt unabhängige Kopien und führt Gruppen gleichen Namens zusammen. | Bestehendes Dashboard und Titel gehen bei der Migration an den ältesten Admin; gab es noch keinen, übernimmt es der erste Admin beim ersten Aufruf. Die Statusprüfung läuft einmal je Ziel-URL, Live-Ereignisse und Status gehen nur an den Besitzer. Kopieren steht allen offen, weil Dashboards keine Geheimnisse enthalten, die nicht ohnehin im selben Netz liegen; falls das nicht gewünscht ist, ließe sich eine Freigabe pro Dashboard nachrüsten. Getroffen am 06.11.2026 mit Matthias (Claude). |
| 15 | Hersteller aus der MAC | Die IEEE-OUI-Liste (MA-L, rund 40.000 Einträge) liegt als `apps/server/src/ipam/oui.json` im Repository und wird in den Server gebündelt; der Browser fragt Hersteller gesammelt über `GET /api/ipam/vendors` ab. Zufällige MACs (lokal-verwaltet-Bit) werden als „Zufällige MAC“ gekennzeichnet. | Kein Abruf zur Laufzeit, funktioniert offline. Quelle ist das npm-Paket `oui-data` (BSD-2-Clause, Daten der IEEE), weil IEEE-Seiten aus der Entwicklungsumgebung nicht erreichbar waren; `scripts/build-oui.mjs` erzeugt die Datei neu. MA-M/MA-S-Blöcke fehlen, solche Geräte zeigen „Unbekannter Hersteller“. Getroffen am 06.11.2026 (Claude). |
| 16 | Passwort vergessen und Rollen | Reset über Einmal-Links: Token mit 32 Zufallsbytes, in `password_resets` nur als SHA-256 gespeichert, ein Link pro Benutzer, per Mail 1 Stunde, vom Admin oder per Kommandozeile 24 Stunden gültig. Mailversand ist optional (SMTP per Umgebungsvariablen, Links nur mit festem `PUBLIC_URL`). Ohne Mail wird die Anfrage beim Benutzer vermerkt und Admins erzeugen den Link in der Benutzerverwaltung. Notzugang für den einzigen Admin: `node dist/main.js reset-link <name>`. Die Rolle `viewer` heißt in der Oberfläche jetzt „Benutzer“. | Viele Homelabs haben keinen Mailserver, deshalb darf der Ablauf nicht davon abhängen. Die Antwort auf „Passwort vergessen“ ist immer gleich und die Mail wird nicht abgewartet, damit weder Inhalt noch Antwortzeit verraten, ob es ein Konto gibt; begrenzt auf 10 Anfragen pro IP in 15 Minuten und 3 pro Konto und Stunde. Das Token steht im URL-Fragment (`#token=`), damit es nicht in Server- oder Proxy-Logs landet. „Nur lesen“ passte nicht mehr, seit jeder sein eigenes Dashboard bearbeitet; intern bleibt der Wert `viewer`, damit keine Datenmigration nötig ist. Getroffen am 07.11.2026 (Claude). |
